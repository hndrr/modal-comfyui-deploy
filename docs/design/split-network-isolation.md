# Splitの外部通信・実行環境の隔離案

検討日: 2026-11-12

> 未実装の検討案です。現在の構成がこの制限を満たしているという説明ではありません。Modal上での成立性・互換性を先に検証し、その結果に基づいて実装範囲を確定します。

## 目的と維持する操作

custom nodeや依存パッケージに悪意あるコードが含まれていても、入力素材・プロンプト・APIキーなどを勝手に外部送信できない構成を目指す。テレメトリの無効化やロゴ取得の停止だけでは、この目的を満たさない。

対象はCPU/GPU分離構成のサーバー側とブラウザ側。既存のGateway・MCP・ジョブ管理・モデル取得処理を活用し、変更を実行環境と権限の境界に集中させる。

プロンプトからのcustom node・モデル追加は維持する。通常の追加操作で、手動のネットワーク切替を要求しない。

| ユーザーの指示 | 維持するMCP操作 |
| --- | --- |
| custom nodeを追加する | `prepare_environment` → `change_node` → `apply_environment` |
| custom nodeを更新する | 候補環境で更新・検証し、成功時に切り替える |
| モデルを追加する | `add_model` → 専用CPUで取得し、`get_admin_operation`で結果確認 |
| 生成する | ワークフロー投入・進捗取得・中断・結果取得 |

ツール名・引数は維持する。追加元の範囲も、現在対応しているRegistryパックとHugging Faceを基本とする。任意の取得元や外部APIへの対応を、この変更に先回りして追加しない。

## 現状と不足している境界

- 現在の候補環境はコード・依存のコピーであり、管理処理から隔離された実行環境ではない。
- `ComfyProcess`は管理側のコンテナ内でComfyUIを起動する。外部通信の強制制限はなく、一部の環境変数を除外しても、悪意あるコードの隔離にはならない。
- Managerのoffline設定やHFのテレメトリ設定は、コードが設定に従うことを前提とする。MCPの`fetch`制限も、任意のPython・別の通信ライブラリ・子プロセス全体を制限するものではない。
- モデル取得は既に専用CPUへ分離されており、この経路を活用できる。
- 外部APIには送信内容を確定して承認する仕組みがある。ただし、承認機能自体はcustom nodeをサンドボックス化しない。

## 提案する構成

既存のMCP操作を残し、custom nodeを読み込む実行部分をModal Sandboxへ分離する。

| 実行場所 | 外部通信 | 渡すデータ・権限 |
| --- | --- | --- |
| Gateway・MCP管理側 | 管理に必要な通信 | ジョブ台帳・管理権限。追加されたノードは実行しない |
| ノードのインストール環境 | 配布元・依存取得先に限定 | 候補のコード・依存のみ。本番素材・履歴・APIキーは渡さない |
| 通常のComfyUI CPU/GPU | 原則全面遮断 | 必要なモデル・入力・出力領域。管理権限・APIキーなし |
| モデルダウンローダー | Hugging Faceへの取得 | モデル保存領域と必要な取得用認証 |
| 外部API専用の実行環境 | 対応済みAPIへの通信 | 承認済みの入力と、そのAPI用のキーだけ |

### 通常のComfyUI実行

- CPUのUI用ComfyUIとCPU/GPUの生成処理を、`block_network=True`のSandboxで実行する。ノードの読み込み時から制限を適用する。
- ノードコード・モデルは読み取り専用とし、必要な入力・出力・設定領域だけを渡す。管理台帳を含むVolume全体は渡さない。
- 起動・停止・HTTP/WebSocket操作を扱う既存の`ComfyProcess`を主な変更箇所とし、Gateway側の呼び出し方をできるだけ維持する。
- GPUはSandbox側だけに割り当てる。管理用コンテナとの二重確保を避け、稼働台数の集計と終了処理も対応させる。
- CPUの事前読み込みが管理側でcustom nodeを実行する経路にならないようにする。現在のMemory Snapshotによる起動時間短縮は、そのまま維持できるとは限らない。

Modal SDKの接続トークンによる認証付きHTTP/WebSocket接続を候補とする。全面遮断との組み合わせはこの環境では未実測であり、最初の成立性検証に含める。

### ノードの追加・更新

既存の候補作成・Managerによる導入・適用判定を活用し、導入時と実行時の権限を分ける。

1. 本番データのない専用Sandboxで、要求されたパックと依存を導入する。候補へユーザーの素材・ワークフロー・履歴・認証情報をコピーしない。
2. 導入後の依存検査、ノード読み込み、CPU/GPU検証を、通信を遮断した環境で行う。
3. 成功した候補のみを稼働版へ切り替える。成功しても、そのコードの通信権限は増やさない。
4. 失敗時は稼働版を維持し、既存の進行状態・エラー・破棄操作で扱う。

管理側では候補環境のPythonやインストールスクリプトを直接起動しない。依存検査も候補のコードが動く可能性のある処理として、隔離内で行う。

実行時にモデルを自動取得するノードは、取得不足として停止させる。そのモデルをプロンプトから追加して再実行する流れにし、失敗を理由に通常実行環境の通信を自動開放しない。コードやモデル領域への書き込みを前提とするノードは、キャッシュ・設定の保存先を含めて互換性を確認する。

この最小案では、インストール環境には限定的な通信を許す。インストールスクリプト自体が悪意を持つ場合もあるため、配布元への通信がすべて無害だと保証する案ではない。そこで本番データや秘密情報を読めないことを重視する。

Modalのドメイン許可リストにはDNSやdomain frontingに関する制約がある。許可先の選定と制限範囲を検証し、これだけで完全な送信防止を保証したとは扱わない。インストール時のコード実行も全面オフラインにする場合は、取得と実行の追加分離が必要で、互換性と変更量を別途評価する。

### モデル取得

既存の`add_model`と専用CPUを維持する。ダウンローダーではcustom nodeを読み込まず、必要な取得用認証を通常のComfyUI実行環境へ渡さない。既存の単一ファイル取得、版の固定、チェックサム確認、上書き禁止を活用する。

### 外部API実行

- 既存の送信内容確認・承認を活用し、一般のcustom nodeを読み込まない固定構成で対応済みAPIを実行する。
- 一般ノードの環境にAPIキーや汎用HTTPプロキシを渡さない。外部送信の許可は管理側で判断する。
- 初版では任意の混在ワークフローを自動分割する仕組みを追加しない。「ローカル処理で保存→対応APIへ送信」の既存方針を使う。
- 新しく追加した任意のAPIノードを、自動的に通信許可の対象にしない。必要な連携は対応済みの経路として個別に扱う。

### ブラウザ側

Python側を遮断しても、custom nodeのJavaScriptがブラウザから送信する経路が残る。

- WorkerでCSPを適用し、外部へのfetch・画像読み込み・WebSocket・フォーム送信などを制限する。
- ComfyUI画面と管理・承認画面を別オリジンに分離する。同じWorkerで配信し、ComfyUI側を制限付きiframeに収める案を検証する。
- ComfyUI側のスクリプトから、管理・承認操作を代行できない境界を設ける。CSPだけで同一オリジンの管理権限を分離したとは扱わない。
- 既存のAccess認証、MCP OAuth、画面操作、アップロード・ダウンロードとの互換性を確認する。

## 最初に行う成立性検証

本番データや本番のAPIキーを渡さない独立した検証環境で、以下を先に確認する。

| 検証対象 | 確認する結果 |
| --- | --- |
| Sandboxへの接続 | 通信全面遮断中でも、認証付きHTTP/WebSocketで画面・進捗・中断を扱える |
| 外向き通信 | テスト用ノードからのHTTP、直接IP接続、DNS、子プロセス経由の送信が拒否される |
| 権限・データ | ノードから管理用Secret・台帳・他の候補環境を読めず、管理用Modal APIを操作できない |
| 導入・切替 | MCPからノード追加・更新・検証・適用・破棄ができ、失敗時は旧環境を維持する |
| モデル・生成 | MCPからモデルを追加し、遮断環境で読み込み・通常生成・結果取得ができる |
| 保存・終了 | 出力の保存完了、環境切替、GPUの終了・台数集計を正しく扱える |
| 外部API | 承認済みの対応APIを専用環境で実行でき、一般ノードからその権限を利用できない |
| ブラウザ | 外部送信・管理操作の迂回・制限を外す遷移が拒否され、必要な画面操作は動く |
| 認証 | Modal側の接続が成立し、未認証アクセスや不正な接続トークンは拒否される |

検討時点のSDKは1.1.4。通常の公開ポートと`block_network=True`の併用には制約があり、接続トークンとサブディレクトリマウントに対応した安定版への更新が必要になる。SDK更新を含めて、全面遮断・接続・Volumeの制限が両立するかを先に確認する。

成立しない場合は、通信制限を緩めて先へ進めず、接続方法・実行境界を見直す。起動時間と費用も検証結果から判断し、現状と同等とは事前に約束しない。

実装後の回帰確認には、既存の環境管理・runtime・worker・MCP承認関連テストを優先する。Workerの変更には対象の既存テストと`npm run typecheck`、画面変更には対象画面の確認を使う。新規テストは通信・権限の境界を保証するものに絞る。

## 変更量と適用方針

これは設定だけの小変更ではなく、MCPの使い方を維持したまま、起動・保存・権限の境界を変える中規模の改修になる。

既存のGateway、候補の状態管理、MCPツール、モデル取得処理を活用する。独立検証、実行・導入境界の実装、外部API・ブラウザ境界の確認、既存操作の回帰確認の順で進め、本番反映は別途扱う。通常構成の変更や、任意の外部サービスに対応する汎用基盤の追加は含めない。

rgthreeのロゴ取得停止やテレメトリ無効化は、不要な通信試行を減らす個別対応として扱う。悪意あるコードに対する防御の代わりにはしない。
