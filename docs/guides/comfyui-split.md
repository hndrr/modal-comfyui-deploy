# CPU/GPU分離構成のComfyUI（Experimental）

> [!NOTE]
> この構成は現在開発・検証中の実験的（Experimental）機能です。

`splitapp.py` は、ComfyUIのUI（Webサーバー）をCPUコンテナで稼働させ、画像生成などの重い処理のみをオンデマンドのGPUコンテナで実行するModalアプリケーション（`comfyui-split`）です。通常構成の `comfyapp.py`（App名: `comfyui`）とは独立して動作し、待機中のGPUコストを抑えながらワークフローの編集・ファイル管理・MCP連携を行えます。

ComfyUI標準のワークフロー作成・編集・保存・読み込みを行うにあたり、任意の外部拡張機能は不要です。

## デプロイと接続

### 1. デプロイ

```bash
./scripts/modal.sh deploy splitapp.py
```

- [Modalプロファイルの設定](../operations/modal-profiles.md)に従ってデプロイを実行します。
- 任意拡張・追加ノード・外部中継は既定で無効です。有効化する場合は[Splitの任意拡張](split-integrations.md)を参照してください。
- **ComfyUI本体のバージョン解決**:
  - 通常デプロイでは、デプロイ時に[公式がLatestに指定した安定リリース](https://github.com/Comfy-Org/ComfyUI/releases/latest)のタグをコミットSHAに解決し、CPU・GPU共通のイメージを構築します（アイドル停止からの復帰時に再取得は行いません）。
  - 既知の版への復旧や本体を更新しない再デプロイでは、デプロイログの `Split ComfyUI revision` に記録されたSHAを指定します。
    ```bash
    SPLIT_COMFYUI_REVISION=<COMFYUI_COMMIT_SHA> scripts/modal.sh deploy splitapp.py
    ```
  - 依存パッケージの保護制約や保存済み環境の移行手順は、[内部仕様・API・検証手順のリリース解決と依存制約](split-internals.md#リリース解決と依存制約の移行)を参照してください。

### 2. ブラウザからの接続（Cloudflare Access）

デプロイ出力に表示される `ui` URL が接続先です。

- **Modal Proxy Authは必須**であり、`COMFYUI_REQUIRES_PROXY_AUTH` による無効化はできません。
- ブラウザから利用する場合は、[Cloudflare Accessの設定手順](../operations/cloudflare-access.md)に従い、Cloudflare Workerの転送先設定、Custom Domain、Accessアプリケーションの宛先および許可ポリシーを設定してください。
  > [!WARNING]
  > Modal側の `MODAL_ORIGINS` にURLを追加するだけでは、公開および認証の設定は完了しません。

### 3. MCPクライアントからの接続

ChatGPT Web、Claude Code、CodexなどのMCPクライアントから利用する場合は、[MCP利用ガイド](../mcp/usage.md)を参照してください（管理者向けの設定手順は[MCPの設定・運用](../mcp/setup.md)に記載）。

通常保存されたGLBメッシュ・SPZ Gaussian splatは、`list_outputs` のファイル名とサブフォルダを `get_3d` に渡して閲覧できます。チャット内表示は最大128 MiBで、表示できないホストやサイズ超過時は認証付きブラウザページを使います。ブラウザの `/view` は通常のページ遷移でビューアーを表示し、`/api/view` は原本を返します。保存済みファイルの表示には、重みの取得や推論環境の追加設定は不要です。導入・更新は[GLB/SPZビューアーの手順](../mcp/setup.md#glbspzビューアーの更新とローカル確認)を参照してください。

ComfyUIの一時プレビューと `.split-temp` 配下は従来どおりComfyUI CPUで扱い、保持・清掃方針を維持します。MCPの保存済み3D取得には含めません。3Dの `inspect_media` は基本メタデータだけを返し、MCPでの3Dアップロード・入力への再利用は非対応です。

## 動作モードとGPU選択

UI上の操作および稼働状態の表示は、同梱の拡張機能 [ComfyUI-Modal-Control](../../extensions/ComfyUI-Modal-Control/README.md) が提供します。標準サイドバーの「GPU」タブ、またはツールバーの `GPU(0)` ボタン（稼働中は赤、取得失敗時は `GPU(?)`）からパネルを開閉できます。

### 2つの動作モード

| 項目 | 分離モード（`split` / 既定） | 常時起動モード（`legacy`） |
| :--- | :--- | :--- |
| **概要** | UIはCPUで稼働し、CPU対象外の生成時のみGPUをオンデマンド起動 | GPUワーカー上でComfyUI全体を常時稼働（通常構成相当） |
| **GPUの稼働** | GPU対象の生成・保存中のみ（完了30秒後に自動停止対象） | 常時稼働（待機中もGPU料金が発生） |
| **UI操作時のGPU** | 起動しない（モデル一覧確認、保存、閲覧もCPUで完結） | 常にGPUが稼働 |
| **切り替え操作** | 「生成時だけ起動に戻す」を押下 | 「GPUを常時起動にする」を押下 |

- **常時起動モードへの切替時**: 画面上のワークフローを自動保存し、切替後に復元します（保存できない場合は切替が中止されます）。
- **常時起動モードの保護**: GPUトンネルはセッション固有のBearer認証で保護され、ブラウザには認証キーを渡しません。また、CPUからのハートビートが90秒途絶えた場合は新規投入を停止し、実行中のキュー完了後にコンテナを終了します。

### GPU稼働状態の表示

- **表示ステータス**: `停止中` / `起動待ち` / `使用中` / `停止待ち` / `常駐中` / `環境検証中` / `確認できません`（取得失敗時は停止と推測せず「確認できません」と表示）。
- **ポーリング動作**: CPUはModal管理APIで各機種のコンテナ数を取得して5秒間キャッシュし、フロントエンドも5秒ごとに `/modal-control/v1/status` を参照します。これらの状態確認でGPUが起動することはありません。
- **配信方式**: ComfyUI本体は変更せず、追加の `custom_nodes` 検索パスから標準の `WEB_DIRECTORY` 経由で配信されます（`/split.js` の独自注入は行いません）。

### GPUの選び方

分離モードの「GPU」パネルで、ジョブごとに使うGPUを選択できます（選択はブラウザに保存され、次回投入ジョブから適用）。

| 選択肢 | CPU自動実行の対象外の場合 |
| :--- | :--- |
| **自動（料金優先）** *(既定)* | 既知APIと軽い入出力だけの処理・検証済み静止画を `L4` に振り分け、未検証ノード・ローカルの動画生成・音楽生成には `RTX PRO 6000` を選択 |
| **自動（速度優先）** | API・軽い入出力は承認待ちがなければ起動中GPUを再利用。ローカル推論には `RTX PRO 6000` を選択 |
| **L4 / L40S / RTX PRO 6000** | 指定したGPU機種を固定で使用（L40Sでの音楽生成なども直接指定で利用可能） |

- CPU対応済みのAPIと軽い読み込み・保存・プレビューだけなら、料金優先・GPU機種の手動指定ではCPUを優先します。速度優先で承認待ちがない場合は、CPU対応済みでも起動中GPUを再利用します。
- パネルの「直近の実行先」には、画面またはMCPから最後に投入されたジョブのCPU/GPU実行先と選択理由が表示されます。
- 判定条件の詳細や、静止画（FLUX.3 Klein）・音楽生成（L40S）の実測データ、再計測手順は **[Split構成のGPU選択と実測データ](split-gpu.md)** を参照してください。

## カスタムノードの管理と互換性

### ComfyUI Managerによるノード追加・更新

分離モードでは、稼働中の環境を壊さないよう「候補環境」を経由してノードを追加・更新します。

1. **候補環境へのインストール**: Managerでのノード追加・更新は、まず「候補環境」に対して行われます。
2. **検証と反映**: Managerの再起動または「ノード更新を反映」を実行すると、依存関係の確認・CPU起動・GPUでのノード読み込み検証（モデル推論は行わない）が実行され、通過すると有効環境が切り替わります。
3. **失敗時のロールバック**: 検証に失敗しても更新前の有効環境が維持されます。「ノード更新を反映」で失敗した候補は `failed` となり同じ候補を再検証できないため、「未反映の変更を取り消す」で候補を破棄すると直ちに生成を再開できます（作り直す場合は破棄後に必要なノード更新を再実行してください）。

**制約事項**:
- ManagerからのComfyUI本体の更新は提供していません。再デプロイすると、指定したSHAまたは公式のLatest安定リリースへ更新します。
- 主要なCUDAパッケージ、フロントエンド、Manager本体のバージョン制約は依存インストール時にも適用されます（保存済み仮想環境との競合・不足を修復する手順は[保存済み環境の移行と手動修復手順](split-internals.md#保存済み環境の移行と手動修復手順)を参照）。
- 生成中・待機中・結果不明のジョブがある場合はモード切替やノード更新を行えません。また、未反映の候補環境が残っている間は新規の生成を受け付けません。

### ノードの互換性と動作の前提

- **CPUで動作する機能**: CPUでインポート可能なカスタムAPIはCPU側でそのまま実行されます。
- **GPU専用ノードの扱い**: 環境検証時に取得したノード定義とJSファイルを配信し、モデルリストと一致する選択肢はCPU側で更新します。
- **常時起動モードが必要なケース**: 独自の動的APIなど、分離モードで再現できない機能を持つノードを利用する場合は「常時起動モード（`legacy`）」へ切り替えて使用してください（あらゆるカスタムノードの動作を保証するものではありません）。

## コンテナとストレージの基本動作

### コンテナの自動起動・停止

- **スケール設定**: CPUサーバー・CPU実行ワーカー・各GPUワーカーともに最小 `0` 台・最大 `1` 台、停止待ち時間（idle timeout）は `30` 秒です（実際に0台へ戻るまでの正確な時間はModalのスケジューラーに依存します）。
- **CPUが稼働・停止する条件**: ブラウザを開いてWebSocket接続や定期通信が続いている間、またはバックグラウンド生成・環境更新の実行中はCPUが1台維持されます。画面を閉じて処理が完了するとCPUも0台へ自動停止します（※常時起動モード中は画面を閉じてもCPU・GPUともに維持されます）。
- **GPUが起動する境界**: 分離モードでは、UI閲覧、ワークフロー保存、ファイル確認などでGPUは一切起動しません。GPUが起動するのは「CPU自動実行の対象外の生成処理」「明示的な環境検証」「常時起動モード」の3つのみです。
- **ストレージ料金**: コンテナが0台の間も、永続化されたModal Volumeのストレージ料金は発生します。

### Volume 一覧

| Volume 名 | 用途 | 共有 / 専用 | 備考 |
| :--- | :--- | :--- | :--- |
| `comfy-model` | モデルデータ | 通常構成と共有 | チェックポイントやLoRAなどの保管 |
| `comfy-inputs` | 入力ファイル | 通常構成と共有 | アップロード画像など |
| `comfy-outputs` | 出力ファイル | 通常構成と共有 | 生成画像の永続保管先 |
| `comfy-user-data` | ユーザーデータ | 初回のみ参照 | 初回起動時に `comfy-split-data/user/` へ複製（SQLiteは複製せず、以降の設定・ワークフローは専用領域を使用） |
| `comfy-split-environments` | 実行環境 | split専用 | ノード、Python仮想環境、検証済みノード定義を保管 |
| `comfy-split-data` | split実行データ | split専用 | `state/`: CPUが書き込むジョブ受付・状態・環境選択<br>`jobs/`: CPU/GPU実行ワーカーが書き込むジョブごとの実行結果 |

- 初回作成時は、Dockerイメージ同梱ノードと `comfy-custom-nodes` Volumeのノードを `comfy-split-environments` へコピーして依存関係を復元します（コピー元Volumeは変更しません）。
- CPUとGPUの間で稼働中のSQLiteファイルを共有することはありません。
