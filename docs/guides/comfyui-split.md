# CPU/GPU分離構成のComfyUI（Experimental）

> [!NOTE]
> この構成は現在開発・検証中の実験的（Experimental）機能です。

`splitapp.py` は、ComfyUI の UI（Web サーバー）を CPU コンテナで常時稼働（またはアイドル時自動停止）させ、画像生成などの重い処理のみをオンデマンドの GPU コンテナで実行する Modal アプリケーション（`comfyui-split`）を構築します。通常構成の `comfyapp.py`（App 名: `comfyui`）とは独立した構成です。

ComfyUI 標準のワークフロー作成・編集・保存・読み込みを行うにあたり、任意の外部拡張機能は必要ありません。

## デプロイと接続

### デプロイ

```bash
./scripts/modal.sh deploy splitapp.py
```

- 本コマンドは、[Modalプロファイルの設定](../operations/modal-profiles.md)に従ってデプロイを実行します。
- 任意拡張・追加ノード・外部中継などの有効化設定は既定で無効です。設定方法や更新手順は[任意拡張](split-integrations.md)を参照してください。

ComfyUI 本体は、デプロイ時に [公式が Latest に指定した安定リリース](https://github.com/Comfy-Org/ComfyUI/releases/latest) のタグをコミット SHA に解決します。版番号の最大値を選ぶ処理ではありません。CPU と GPU はその SHA の共通イメージを使い、アイドル停止からの復帰時には再取得しません。フロントエンドはそのリリースの `requirements.txt`、Manager は `manager_requirements.txt` に従います。

GPU 用の wheel と、それらがこの環境で必要とする依存パッケージは、ベースイメージにインストールされた版を維持します。wheel のメタデータから依存をたどるので、PyTorch・SageAttention に加え、Triton や cuDNN なども対象になります。ComfyUI やカスタムノードの依存関係がこれらと衝突する場合、またはリリースを取得できない場合はデプロイが失敗し、稼働中のデプロイはそのまま残ります。

既知の版への復旧、本体を更新しない再デプロイ、GPU 検証では、デプロイログの `Split ComfyUI revision` に記録された SHA を指定します。指定時は GitHub のリリース API を呼びません。通常のデプロイでは、未設定・空欄・空白のみなら Latest を選びます。GPU 検証では引き続き SHA の指定が必須です。

```bash
SPLIT_COMFYUI_REVISION=<COMFYUI_COMMIT_SHA> scripts/modal.sh deploy splitapp.py
```

自動選択時の API 呼び出しには、ローカルの `GH_TOKEN` または `GITHUB_TOKEN` があれば使用します。トークンをイメージに記録することはありません。API の失敗時に未確認の版へ切り替えるフォールバックは行いません。

ビルド時には依存関係に加え、CPU 上で `PromptQueue.put` のガード設置とジョブの整形 API を検査します。全カスタムノードや画面・生成処理の互換性を保証する検査ではないため、本体更新時は後述の実機検証も必要です。起動後・運用中の失敗まで自動ロールバックする仕組みではありません。

### 依存制約の更新と保存済み環境の移行

wheel の依存は NumPy、Pillow、setuptools なども含めて固定します。異なる版を要求するノードは、その環境ではインストールできません。セキュリティ修正版などへ更新する場合は `MODAL_FORCE_BUILD=1` を付けてベースから再ビルドし、新しい制約で検証してください。既存イメージの制約を Manager から無効にする運用は想定していません。

既存の保存済み venv は再デプロイ時に書き換わりません。新しく固定対象になった依存を venv 内で上書きしていると、「ノード更新を反映」や自動更新の検証が失敗します。失敗した候補は採用されず、有効環境は維持されます。

フロントエンド・Manager・comfy-kitchen・SageAttention は、CPU/GPU ともにイメージの `/opt/split-core` を優先して読み込みます。保存済み venv に旧版が残っていても、これらはイメージ側の固定版を使います。

「ノード更新を反映」の検証に失敗した候補は `failed` になり、同じ候補を反映ボタンから再検証できません。「未反映の変更を取り消す」で候補を破棄してから作り直し、必要なノード更新も再実行してください。以下の手順で行う手動検証だけが失敗した場合は、同じ編集中の候補を修復できます。

1. Manager で候補環境を作り、反映前に候補の Python で `-m comfy_split.check_environment` を実行して、検証エラーに出るパッケージを確認します。
2. CPU コンテナで候補の `venv/bin/python -m pip show <PACKAGE>` を実行し、`Location` が候補の venv 内であることを確認します。その候補だけで `venv/bin/python -m pip uninstall <PACKAGE>` を行うと、`--system-site-packages` によりイメージ側の版が使われます。有効環境やイメージ自体のパッケージは削除しません。
3. 同じ候補の Python で `-m comfy_split.check_environment` を実行し、Manager の「ノード更新を反映」で通常の CPU/GPU 検証を通してから採用します。
4. ノード自体が旧版を要求する場合は、候補内で対応版へ更新するか、その候補を破棄します。本体更新前の構成へ戻す場合は、既知の SHA と元のイメージ定義を使って再デプロイします。

`pip check` が版の競合ではなく依存の不足を報告する場合もあります。以前のイメージから継承していた依存が、新しいイメージに含まれなくなった場合です。エラーに示された要求を候補の `venv/bin/python -m pip install -c /opt/split-constraints.txt '<REQUIREMENT>'` で補い、手順3の検証を通してください。

### ブラウザからの接続（Cloudflare Access）

接続先はデプロイ出力に表示される `ui` URL です。

- **Modal Proxy Auth は必須**であり、`COMFYUI_REQUIRES_PROXY_AUTH` による無効化はできません。
- ブラウザから利用する場合は、[Cloudflare Accessの設定手順](../operations/cloudflare-access.md)に従い、Cloudflare Worker の転送先設定、Custom Domain、Access アプリケーションの宛先および許可ポリシーを設定してください。
  > [!WARNING]
  > Modal 側の `MODAL_ORIGINS` に URL を追加するだけでは、公開および認証の設定は完了しません。

### MCP クライアントからの接続

ChatGPT Web、Claude Code、Codex などの MCP クライアントから利用する場合は、本構成専用の[MCP 利用ガイド](../mcp/usage.md)を参照してください。管理者向けの接続先設定手順は[MCP の設定・運用](../mcp/setup.md)に記載されています。

## 動作モードとUI操作

### 2つの動作モード

| 項目 | 分離モード（`split` / 既定） | 常時起動モード（`legacy`） |
| :--- | :--- | :--- |
| **概要** | UI は CPU で稼働し、生成時のみ GPU をオンデマンド起動 | GPU ワーカー上で ComfyUI 全体を常時稼働（通常構成相当） |
| **GPU の稼働** | 生成・保存の処理中のみ（完了 30 秒後に自動停止対象） | 常時稼働（待機料金が発生） |
| **UI 操作時の GPU** | 起動しない（モデル一覧確認、保存、閲覧も CPU で完結） | 常に GPU が稼働 |
| **切り替え方法** | 「生成時だけ起動に戻す」を押下 | 「GPUを常時起動にする」を押下 |

- **常時起動モードへの切替時**: 画面上のワークフローを自動保存し、切替後に復元します（保存できない場合は切替が中止されます）。
- **常時起動モードのセキュリティ**: GPU トンネルはセッション固有の Bearer 認証で保護され、ブラウザには認証キーを渡しません。
- **無通信時の保護**: 常時起動モード時、CPU からのハートビートが 90 秒途絶えた場合は新規投入を停止し、実行中のキューが完了した後にコンテナを終了します。

### モード共通の UI と状態表示

UI の操作および状態表示は、独立した拡張機能 [ComfyUI-Modal-Control](../../extensions/ComfyUI-Modal-Control/README.md) によって提供されます。

- **パネルの開閉**:
  - 標準サイドバーの「GPU」タブ、または標準ツールバーの `GPU(0)` ボタン（稼働中は赤、取得失敗時は `GPU(?)`）から開閉できます。
  - モード変更ボタンは折りたたまれず常に表示されます。
- **状態表示**:
  - 表示状態: `停止中` / `起動待ち` / `使用中` / `停止待ち` / `常駐中` / `環境検証中` / `確認できません`（取得失敗時は停止と推測せず「確認できません」と表示）。
  - CPU は各機種のコンテナ数を Modal の管理 API で取得し、合計を 5 秒間キャッシュします。
  - フロントエンド画面も 5 秒ごとに `/modal-control/v1/status` をポーリングして状態を更新します。
  - これらの状態確認処理によって GPU ワーカーが起動することはありません。
- **配信方式**:
  - 標準の `WEB_DIRECTORY` 経由で配信され、ゲートウェイによる `/split.js` の追加配信は行いません。ComfyUI 本体のコードは変更せず、追加の `custom_nodes` 検索パスから読み込まれます。

### 次の生成に使うGPU

分離モードの「GPU」パネルで **自動（料金優先）／自動（速度優先）／L4／L40S／RTX PRO 6000** を選べます。既定は料金優先です。選択はそのブラウザに保存され、次に受け付けたジョブから適用されます。画面上の選択や状態確認でGPUは起動しません。「直近の受付」には、画面またはMCPから最後に投入されたジョブの機種と優先設定を含む選択理由が表示されます。

自動では、実行する枝に含まれるノードを調べます。料金優先は検証済みの静止画を実測料金で振り分け、速度優先はローカル推論にRTX PRO 6000を選びます。未検証のモデル・カスタムノードやローカルの動画生成・フレーム処理にはRTX PRO 6000を選びます。外部APIで生成した動画や既存の動画ファイルを読み込み・保存するだけの処理は、ファイルの大きさによらず軽い入出力として扱います。GPUを直接指定すると、その機種を使います。

既知の外部APIと軽い素材入出力だけのジョブは、料金優先ではL4を選びます。速度優先で承認待ちを経ずに投入できる場合は、受付時に起動中と確認できたGPUを使い、機種切替による停止待ちと再起動を減らします。起動中の機種を確認できなければL4です。

MCPで外部APIの承認が必要な場合は、承認待ちの間にGPUが停止しうるため、起動状態を使わずグラフから機種を決めます。外部APIと軽い入出力だけなら速度優先でもL4です。後段のローカル処理も判定対象に含め、明示した機種指定を優先します。選択結果は承認待ちを含め受付時に固定します。

速度優先でも初回はGPUの割り当て・起動・モデル読み込み時間が加わります。機種を変えるときは前のコンテナが停止するまでキューで待ちます。待機中のジョブは通常どおりキャンセルできます。常時起動とノード環境検証にはデプロイ時のGPUプロファイルを使います。

静止画の実測対象は FLUX.3 Klein の int8 版です。SageAttention 有効、バッチ1、正方形512または1024、Euler・simple・4ステップ・CFG 1 のテキストからの生成を対象とします。モデル、テキストエンコーダー、VAE、実行ノード、入力条件を照合するので、ノードIDや保存名は自由です。

比較は機種・解像度ごとにGPUが0台の状態から始めます。ComfyUIの起動からモデル読み込み、生成、PNG保存の確認までを測り、[ModalのGPU秒単価](https://modal.com/pricing)を掛けて比べます。表の金額はこの区間のGPU料金の目安です。GPUの割り当て待ちやコンテナの初期化、生成後のアイドル時間、外部API料金は計算の対象外です。

| 初回生成（各条件1回） | L4（$0.000222/秒） | L40S（$0.000542/秒） | 料金優先の選択 |
| --- | --- | --- | --- |
| 512 × 512 | 50.16秒・$0.01114 | 23.17秒・$0.01256 | L4 |
| 1024 × 1024 | 37.20秒・$0.00826 | 26.84秒・$0.01455 | L4 |

各解像度を別の初回生成として計測しています。モデル読み込みやVolumeキャッシュなど実行条件の揺らぎも含む単発の観測値で、512pxから1024pxへの解像度変更による速度差を測ったものではありません。

速度優先の判断に使った、同じ1024pxグラフのモデル読み込み済みでのComfyUI実行時間はL4が2.79秒、L40Sが0.91秒、RTX PRO 6000が0.67秒です。各機種1回の測定で、初回起動を含む上表とは計測区間が異なります。

同じ[検証用グラフ](../../scripts/verify_split_gpu_workflow.json)を3機種で再計測するには `SPLIT_COMFYUI_REVISION=<DEPLOYED_COMFYUI_SHA> scripts/modal.sh run -m scripts.verify_split_gpus` を使います。SHA の指定は必須で、`.env` からも読み込みます（シェルでの指定を優先）。結果にも実際の SHA を記録します。`--gpu L4 --size 1024` のように対象を絞れます。モデルVolumeは読み取り専用で、検証用PNGは一時領域に保存します。イメージは現在のチェックアウトから構築するため、本番との比較には同じリポジトリのコミットとデプロイ設定も使用してください。

#### L40Sでの音楽生成の実測

2026-11-06に、保存済みの成功ワークフローを基に、バッチ1・SageAttention有効で各条件を1回実行しました。モデルは既存Volumeから読み取り、ケースごとにGPUを停止してから次を起動しています。以下の4件はすべて生成とMP3保存に成功しました。

| モデル | 音声の長さ | ComfyUI実行時間 | ComfyUI起動から保存まで | 観測最大VRAM |
| --- | --- | --- | --- | --- |
| ACE-Step 1.5 XL Turbo bf16 | 30秒 | 22.83秒 | 41.43秒 | 16.0 GiB |
| ACE-Step 1.5 XL Turbo bf16 | 180秒 | 27.70秒 | 40.00秒 | 29.7 GiB |
| YuE2 3B bf16 | 30秒 | 32.75秒 | 48.08秒 | 9.0 GiB |
| Stable Audio 3 Medium | 30秒 | 10.74秒 | 26.17秒 | 6.6 GiB |

- ACE-StepはQwen 0.6B＋1.7BのエンコーダーとACE 1.5 VAEを使用。音声コード生成あり、Euler/simple・8ステップ・CFG 1です。
- YuE2はfullモード、dpm_2/sgm_uniform・32ステップ・CFG 1、タイルVAEデコードです。
- Stable AudioはT5Gemmaエンコーダー、lcm/simple・8ステップ・CFG 1です。

VRAMは生成中に約250ms間隔で取得したデバイス全体の使用量です。MP3のデコード、指定時間との一致、有限値かつ無音でない音声データ、各試行後のGPU 0台復帰も確認しました。実行時間はモデル読み込みを含み、GPUの割り当て待ち・コンテナ初期化は表の時間に含みません。

この条件ではL40Sを直接指定して生成できます。音楽についてはL4・RTX PRO 6000との同条件の料金比較が残っており、自動選択はRTX PRO 6000を使います。

### ComfyUI Manager によるノード追加・更新

- **候補環境へのインストール**:
  - 分離モードでは、ノードの追加・更新は直接有効環境には反映されず、「候補環境」に対して行われます。
- **反映プロセス**:
  - インストール完了後に Manager を再起動するか、「ノード更新を反映」を実行すると、依存関係の確認、CPU 起動、GPU でのノード読み込み検証が行われ、問題がなければ有効環境が切り替わります。
  - GPU での読み込み検証ではモデル生成は行われません。
  - 検証失敗時は更新前の有効環境が維持されます。「未反映の変更を取り消す」で候補を破棄すれば、直ちに生成を再開できます。
- **制約事項**:
  - Manager からの ComfyUI 本体の更新は提供していません。再デプロイすると、指定した SHA または公式の Latest 安定リリースへ更新します。
  - 主要な CUDA パッケージ、フロントエンド、Manager 本体の制約は依存関係のインストール時にも適用されます。
  - 生成中・待機中・結果不明のジョブが存在する場合は、モード切替およびノード更新を拒否します。
  - 候補環境が残っている間は新規の生成を受け付けません。

## ライフサイクルとスケーリング

### コンテナの自動起動・停止

- **最小・最大台数**: CPU サーバー、GPU ワーカーともに最小 0 台・最大 1 台で動作します。
- **停止待ち時間（idle timeout）**: 停止待ちは 30 秒に設定されています（※30 秒は設定値であり、実際にコンテナが 0 台へ戻るまでの正確な時間は Modal のスケジューラーに依存します）。
- **CPU の自動停止**: ブラウザ画面を閉じ、生成キューや環境更新処理がなくなると CPU も自動的に停止します（※常時起動モードでは画面を閉じても CPU と GPU を維持し続けるため自動停止しません）。画面を開いて WebSocket 接続や定期リクエストが継続している間は CPU が稼働し続けます。
- **バックグラウンド処理時の維持**: バックグラウンド生成や環境更新の実行中は、Modal の autoscaler によって CPU が一時的に 1 台維持され、処理と保存の完了後に最小 0 台へ戻ります。
- **GPU 起動の境界**: 分離モードでは、UI 閲覧、WebSocket 通信、ワークフロー保存、ファイル閲覧などの操作で GPU が起動することはありません。GPU は生成処理、明示的な環境検証、および常時起動モードでのみ使用されます。
- **ストレージ料金**: コンテナが停止している間も、永続化された Volume のストレージ料金は発生します。

### CPU 起動プロセスと初期化画面

1. **Gateway 先行起動**: HTTP の入口（Gateway）は環境更新処理より先に起動するため、起動中であっても `GET /split/startup` で進行段階を確認できます。
2. **起動画面の表示**: 準備中はトップページに専用の起動画面が表示されます。
3. **リクエスト待機**: `/split/startup` 以外の API リクエストは最大 20 秒間待機し、準備が完了しない場合は `503 Service Unavailable`（`Retry-After: 2`）を返します。
4. 起動確認や画面表示のみで GPU が起動することはありません。保存領域の清掃は起動完了後のアイドル処理で行われます。

### CPU Memory Snapshot による高速復帰

停止状態から再度画面を開いた際は、CPU コンテナの起動・復元が行われます。

- CPU Memory Snapshot が利用可能で、かつスナップショット保存時と有効環境のバージョンが一致している場合は、初期化済みの ComfyUI プロセスを高速に再利用します。
- 一致しない場合や利用できない場合は通常起動を行います。
- 復元完了後は、最新のジョブ状態とユーザーデータを再読み込みします（詳細は [CPU復元の詳細](../design/cpu-memory-snapshot.md#本体への組み込み) を参照）。

### ノードパックの自動更新

`SPLIT_NODE_PACKS` で指定したノードパックは、デプロイ後の最初のアイドル時（CPU 起動時）に更新を確認します。

- カタログに `revision` が指定されている場合は固定コミットを、指定がない場合は配布元リポジトリの既定ブランチ（HEAD）を使用します。
- 変更が検出された場合は、候補環境を作成して依存関係と CPU での読み込みを検査した上で採用します（この自動更新で GPU は起動しません）。
- 更新に失敗した場合は更新前の有効環境を引き続き使用します（再試行条件は [取得と更新](split-integrations.md#取得と更新) に準拠）。
- CPU と GPU は、ジョブに固定された同一の環境バージョンを使用します。

## ストレージ構成とデータ管理

### Volume 一覧

| Volume 名 | 用途 | 共有 / 専用 | 備考 |
| :--- | :--- | :--- | :--- |
| `comfy-model` | モデルデータ | 通常構成と共有 | チェックポイントや LoRA などの保管 |
| `comfy-inputs` | 入力ファイル | 通常構成と共有 | アップロード画像など |
| `comfy-outputs` | 出力ファイル | 通常構成と共有 | 生成画像の永続保管先 |
| `comfy-user-data` | ユーザーデータ | 初回のみ参照 | 初回起動時に `comfy-split-data/user/` へ複製（SQLite ファイルは複製せず、以降の設定・ワークフローは専用領域を使用） |
| `comfy-split-environments` | 実行環境 | split 専用 | ノード、Python 仮想環境、検証済みノード定義を保管 |
| `comfy-split-data` | split 実行データ | split 専用 | `state/`: CPU が書き込むジョブ受付・状態・環境選択<br>`jobs/`: GPU が書き込むジョブごとの実行結果 |

- **初期環境の構築**: 初回作成時、Docker イメージ同梱のノードと `comfy-custom-nodes` Volume のノードを環境 Volume へコピーし、依存関係を復元します（コピー元の Volume は変更しません）。
- **稼働中の SQLite 非共有**: CPU と GPU で稼働中の SQLite ファイルを共有することはありません。

### 入出力のコミットと UI 通知の整合性

- **実行順序**:
  1. GPU は入力ファイルを reload した後に生成処理を実行します。
  2. 出力ファイルを commit した後に結果を保存します。
  3. CPU は出力ファイルを reload してからクライアントへ完了を通知します。
- **通知の保留**: `execution_success` やエラー通知は、出力ファイルの公開と履歴の保存が完了するまで保留されます。
- **フロントエンドの Total 表示対策**: `executed` イベントで完了ノード数を数えるフロントエンドに合わせ、`progress_state` で完了した出力なしノードに対しても空の UI 結果を 1 回通知します。実際の画像・動画を含む結果は出力公開後に通知されます。本体更新時は対応するフロントエンドで Total 表示とプレビューを確認してください。
- **一時出力（temp）の処理**:
  - 一時ファイルはコンテナのローカル作業領域で生成され、GPU ワーカーが出力 Volume の `.split-temp/<起動ID>/` へコピーします。
  - 履歴および完了イベントの参照を永続出力へ変換した上で公開します（`.split-temp/temp` に保存された一時出力も `type=temp` で参照・閲覧可能）。
- **ジョブ受付日時の補完**: 待機中・実行中のジョブおよび履歴には受付日時を付与し、保存済みの失敗履歴に不足している項目も補完します。これにより、1 件の失敗ジョブが原因で Media Assets の一覧全体が読み込めなくなる不具合を防ぎます。

### 自動清掃（クリーンアップ）ルール

保存領域の清掃は、**分離モードのアイドル時（GPU コンテナ数および待機呼び出しがともに 0 である状態）**に行われます。停止中に清掃のためだけに CPU や GPU を起動することはありません。詳細な設計は [保存構成の設計・変更記録](../design/split-storage.md) を参照してください。

- **環境 Volume（`comfy-split-environments`）**:
  - 保護対象: 初期環境、有効環境、候補環境、未完了処理が参照している環境、CPU Memory Snapshot が参照している環境（`comfy-split-environments/.cpu-snapshots/` に記録）。
  - 上記以外の古い環境は清掃対象となり、無期限に保管されることはありません。
- **ジョブ履歴**:
  - 完了時刻が記録された終了済みジョブの詳細履歴は、7 日経過後に清掃対象となります。
  - 結果不明のジョブは期限経過でも自動削除されず、再実行を防止するための最小限の記録が保持されます。
- **一時ファイル（`.split-temp`）**:
  - 更新から 24 時間以上経過し、かつ履歴や処理から参照されていないファイルは清掃対象となります。
  - 通常の生成物、入力ファイル、保存済みワークフローが自動削除されることはありません。

## API仕様と障害復旧

### ComfyUI 標準 API とプロキシ中継

- `/prompt`、`/queue`、`/history`、`/ws`、および `/api/*` を中継・処理します。
- 分離モードでは、キュー受付、履歴取得、キャンセル、重複受付防止を CPU 側で処理します。常時起動モードでは、これらのリクエストを GPU 上の ComfyUI へ中継します。
- ジョブ一覧 API は外部キューのスナップショットを標準拡張へ渡して整形します（ComfyUI 内部のキュー・履歴メソッドは差し替えません）。

> [!NOTE]
> **ASGI パスの再エンコード問題（Modal 1.1.4 対策）**  
> Modal 1.1.4 の標準 Web サーバー中継はデコード済み ASGI パスを転送するため、`/userdata/workflows%2Fname.json` のような URL エンコードされたファイルパスの保存・読み込みに失敗します。  
> そのため、CPU の入口は認証付き ASGI アプリとして構成し、`comfy_split/modal_proxy.py` でパスを再エンコードして固定版 Modal の中継へ渡しています（環境から `raw_path` が提供されている場合はそれを優先）。Modal SDK 更新時は `tests/split/test_proxy.py` および公開 URL 経由でのワークフロー保存・読込を確認してください。

### 追加 API 一覧

| パス | メソッド | 説明 |
| :--- | :--- | :--- |
| `/split/startup` | `GET` | 起動段階、準備完了・失敗ステータス、CPU Snapshot の復元情報を取得 |
| `/split/status` | `GET` | 現在の動作モード、環境更新状況、結果不明ジョブの有無を取得 |
| `/modal-control/v1/status` | `GET` | 上記と同じ状態を返すバージョン付き API（`api_version: 1`） |
| `/split/mode` | `POST` | 動作モードを切り替え（`{"mode": "split"}` または `{"mode": "legacy"}`） |
| `/split/environment/apply` | `POST` | 候補環境を作成・検証して有効環境に反映 |
| `/split/environment/discard` | `POST` | 未反映の候補環境を破棄 |
| `/split/environment/repair-image-browsing` | `POST` | Image Browsing をイメージ同梱版へ戻す候補環境を作成・検証して反映 |
| `/jobs/<id>/cancel` | `POST` | 指定ジョブの待機キャンセル、または GPU ワーカーへの中断指示 |
| `/jobs/cancel` | `POST` | 複数ジョブの一括キャンセル（`{"job_ids": ["<id>", ...]}`） |

#### 特殊なリクエストヘッダー

- **`Idempotency-Key`（`/prompt` へのリクエスト時）**:
  - 同一キーかつ同一内容の再送に対しては、新規ジョブを作成せず同じジョブ ID を返します。
  - 同一キーでリクエスト内容が異なる場合は `409 Conflict` で拒否します。
- **`X-Modal-Execution-Mode: split`（標準 ComfyUI API へのリクエスト時）**:
  - 外部クライアントが明示的に分離モードでの実行を要求するヘッダーです。
  - 常時起動モード中にこのヘッダー付きでリクエストが届いた場合、GPU への不要な転送を防ぐため `409 Conflict` を返します（状態取得やモード切替などの管理 API は拒否の対象外です）。通常のブラウザ画面はこのヘッダーを付与しないため、両モードを柔軟に切り替えて利用できます。

### 依存関係レポート（dependencies）

`/modal-control/v1/status` の `dependencies` フィールドは、実行中の CPU ComfyUI 環境における `comfy-kitchen` のバージョン、固定バージョン、および必須 API の不足状況を返します（※GPU カーネルの動作検証とは区別されます）。

- `comfy-kitchen` は上流 ComfyUI の指定バージョンを固定依存に含め、イメージ構築時および仮想環境適用時に検査します。
- 保存済み仮想環境が固定版と異なるパッケージを優先している場合は、CPU 側のレポートに反映されます。
- 修正が必要な場合は Manager で候補環境の依存を直し、「ノード更新を反映」で検証・採用します（環境検証自体が自動で依存を修復するわけではありません）。

### ジョブの整合性と二重実行防止（障害復旧）

- **2 段階コミットによるディスパッチ**:
  1. CPU は GPU 呼び出し前に `dispatch intent`（投入意図）を保存します。
  2. Modal の呼び出し ID を取得した後に確定情報を保存します。
  3. この間に CPU が停止して ID を記録できなかった場合、ジョブ状態は `unknown`（結果不明）となり、GPU 側の結果記録を待ちます。
- **GPU 側の重複実行防止**:
  - GPU 側も実行前に開始記録を commit します。
  - 同一ジョブ ID で GPU 関数が再度呼び出された際、すでに保存済みの結果があればそれを返します。開始記録しか残っていない場合は `unknown` とし、再実行を行いません。
- **結果不明（`unknown`）ジョブの復旧**:
  - 結果不明となったジョブは自動再実行されず、後続ジョブの実行も一時停止します。
  - 管理者は Modal の GPU 呼び出しログおよび `comfy-split-data/jobs/` の状態を確認した上で手動復旧を行ってください。
  - ネットワークエラーの発生のみを根拠に安易にジョブを再投入してはいけません。
  - なお、GPU 関数の実行タイムアウトは「失敗」として確定処理され、結果待ちポーリングのタイムアウトとは区別されます。
- **再デプロイ時の注意事項**:
  - CPU を再デプロイする際は、旧バージョンの CPU コンテナが完全に停止してから新しい CPU を利用してください。状態 Volume への複数デプロイからの同時書き込みはサポートされていません。
  - 通常構成（`comfyapp.py`）を別途起動している場合、その GPU は split 構成の台数制限（最大 1 台）や UI 上の台数表示には含まれません。

## 検証・テスト手順

### ノードの互換性と動作の前提

- CPU でインポート可能なカスタム API は CPU 側で実行されます。
- GPU 専用ノードについては、検証時のノード定義と JS ファイルを配信し、モデルリストと一致する選択肢は CPU 側で更新します。
- 独自の動的 API など、分離構成で再現できない機能を持つノードには常時起動モードを使用してください。
- あらゆるカスタムノードの動作を保証するものではありません。

### ログとメトリクスの確認

- 構造化ログに含まれる `comfy_ready`、`gpu_ready`、`gpu_finished` で起動時間および総処理時間を確認できます。
- モデル読み込みの詳細な所要時間は ComfyUI 内部ログで、コンテナの停止状況は Modal Containers 管理画面で確認してください（※GPU Memory Snapshot は本構成では未使用です）。

### ローカル単体テスト

ローカル環境での回帰テストは以下のコマンドで実行します。

```bash
uv sync --locked --extra split-test
uv run --locked --extra split-test python scripts/test_standalone.py --suite split
```

全体のテスト構成や任意拡張との連携検証については [テストの説明](../../tests/README.md) を参照してください。

### 実機検証観点と検証スクリプト

実機での受け入れ確認では、ローカルのプロトコルテストだけでなく以下の観点を確認します。

- GPU 0 台の状態で 10 分間ワークフローの編集・保存・閲覧を継続できること
- 画像生成およびリアルタイムプレビューが正常に機能すること
- 生成完了後、停止待ち設定（30 秒）に従って GPU が正常に停止すること
- 連続生成、切断後の再接続、Manager によるノード更新と失敗時の復帰、モードの往復切り替えが正常に行えること

コンテナ内で実行可能な自動検証スクリプトは以下の通りです（いずれも接続先はコンテナ内部の `http://127.0.0.1:8000` を使用し、`SPLIT_URL` は使用しません）。

| スクリプト | 実行場所 / 所要時間 | 検証内容 | 備考 |
| :--- | :--- | :--- | :--- |
| `scripts/verify_split_execution.py` | CPU コンテナ内<br>（短時間） | 2 件の投入と待機キャンセル、画像保存・表示、WebSocket イベント、モード往復、GPU 停止を確認する API スモークテスト | `EmptyImage` を使用するため、モデル推論やサンプリング中プレビューの検証は含みません |
| `scripts/verify_split_idle.py` | CPU コンテナ内<br>（約 10 分間） | WebSocket を維持しながら、画面配信、メタデータ取得、画像アップロード・表示、ワークフロー保存・読取を繰り返し、各回で GPU 台数が常に 0 であることを確認 | 検証用ファイルは `split-verification` 名で保存されます |
| `scripts/verify_image_browsing.py` | 修復後 CPU コンテナ内 | Web 拡張配信、一覧表示、アップロード、プレビュー、名前変更、削除、MiniMax 生成結果参照を確認 | 出力 Volume の `split-verification/` に `minimax_real_` で始まる画像が存在することが前提です |

> [!IMPORTANT]
> これらのスクリプトによる API テストの完了とは別に、Cloudflare Access を経由した実ブラウザでの操作確認が必須です。

### Image Browsing の修復と検証

Docker イメージを更新しただけでは、Volume 上に保存されている既存ノードは自動更新されません。

1. **修復候補環境の作成**:
   - 認証済みの split CPU エンドポイントへ `POST /split/environment/repair-image-browsing` を送信します。
   - アクティブ環境を複製し、Image Browsing のみをイメージ同梱版に戻した候補環境が作成されます（他の追加済みノードも候補環境へ引き継がれます）。
   - 依存関係の検査、CPU および GPU での読み込み検証を通過した後に有効化されます。
   - ※GPU 検証時に一時的な GPU 起動を伴います。
   - ※生成中、キュー待機中、または別の候補環境が存在する場合は `409 Conflict` で拒否されます。
2. **結果確認とロールバック**:
   - 結果は `/split/status` の `candidate` および `environment` で確認できます。
   - 失敗した場合は更新前の有効環境が維持されます。「未反映の変更を取り消す」で候補を破棄してから生成を再開してください。
3. **API 検証の実行**:
   - 修復完了後、GPU が 0 台に戻ったことを確認した上で `scripts/verify_image_browsing.py` を実行します（スクリプト自身が作成した検証ファイルのみ削除されます）。

## ComfyUI本体との内部連携

- **起動方式**: ComfyUI は `python main.py` で通常通り起動します。キュー読み取り、履歴管理、生成スレッド、一時ファイル削除といった内部処理は上書きしません。分離モードにおける生成受付と GPU への投入は Gateway が担います。
- **ComfyUI-Modal-Bridge の役割**:
  - [ComfyUI-Modal-Bridge](../../extensions/ComfyUI-Modal-Bridge/README.md) は、CPU への直接生成投入を拒否する `PromptQueue.put` ガード機能や、ノード定義取得・ジョブ整形・CPU 復元用の内部 API を提供します。
  - これらの内部 API は外部公開 Gateway からは直接アクセスできません。本拡張は split 構成に必須のコンポーネントであり、任意の AgentBridge 中継とは異なります。
- **Manager とパッチの適用関係**:
  - Manager によるインストール処理は候補環境へ中継されます。
  - 通常構成（`comfyapp.py`）で使われている WebSocket 圧縮パッチや `user_manager` へのソースパッチは、split 構成には適用されません。
- **内部境界変更時の検証**:
  - Bridge や Gateway との連携境界を変更した際は、`scripts/verify_comfy_bridge.py` による CPU ガードおよびジョブ API の検証に加え、実モデルでの生成・プレビュー、通常出力・一時出力の保存、CPU 再起動後の復元、二重実行防止の動作確認を必ず実施してください。
