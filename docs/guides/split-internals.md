## リリース解決と依存制約の移行

### デプロイ時のComfyUIリリース解決とwheel保護

- **安定リリースの解決**:
  - デプロイ時に[公式がLatestに指定した安定リリース](https://github.com/Comfy-Org/ComfyUI/releases/latest)のタグをコミットSHAに解決します（版番号の最大値を選ぶ処理ではありません）。
  - CPUとGPUはそのSHAの共通イメージを使い、アイドル停止からの復帰時には再取得しません。
  - フロントエンドはそのリリースの `requirements.txt`、Managerは `manager_requirements.txt` に従います。
- **SHA明示指定によるデプロイ・検証**:
  - 既知の版への復旧、本体を更新しない再デプロイ、およびGPU検証では、デプロイログの `Split ComfyUI revision` に記録されたSHAを指定します（指定時はGitHubのリリースAPIを呼びません）。
  - 通常のデプロイでは未設定・空欄・空白のみならLatestを選びますが、GPU検証では引き続きSHAの指定が必須です。
    ```bash
    SPLIT_COMFYUI_REVISION=<COMFYUI_COMMIT_SHA> scripts/modal.sh deploy splitapp.py
    ```
  - 自動選択時のAPI呼び出しには、ローカルの `GH_TOKEN` または `GITHUB_TOKEN` があれば使用します（トークンをイメージに記録することはなく、API失敗時に未確認の版へ切り替えるフォールバックも行いません）。
- **GPU用wheelと依存パッケージの保護**:
  - GPU用のwheelと、それらがこの環境で必要とする依存パッケージは、ベースイメージにインストールされた版を維持します。wheelのメタデータから依存をたどるため、PyTorch・SageAttentionに加え、TritonやcuDNN、NumPy、Pillow、setuptoolsなども固定対象になります。異なる版を要求するノードは、その環境ではインストールできません。
  - ComfyUIやカスタムノードの依存関係がこれらと衝突する場合、またはリリースを取得できない場合はデプロイが失敗し、稼働中のデプロイはそのまま残ります。
  - セキュリティ修正版などへ更新する場合は `MODAL_FORCE_BUILD=1` を付けてベースから再ビルドし、新しい制約で検証してください（既存イメージの制約をManagerから無効にする運用は想定していません）。
- **ビルド時の自動検査**:
  - ビルド時には依存関係に加え、CPU上で `PromptQueue.put` のガード設置とジョブの整形APIを検査します。
  - 全カスタムノードや画面・生成処理の互換性を保証する検査ではないため、本体更新時は[後述の実機検証](#検証テスト修復手順)も必要です（起動後・運用中の失敗まで自動ロールバックする仕組みではありません）。

### 保存済み環境の移行と手動修復手順

- **イメージ優先パッケージと保存済みvenvの扱い**:
  - フロントエンド・Manager・`comfy-kitchen`・SageAttentionは、CPU/GPUともにイメージの `/opt/split-core` を優先して読み込みます（保存済みvenvに旧版が残っていてもイメージ側の固定版を使用）。
  - 既存の保存済みvenvは再デプロイ時に書き換わりません。新しく固定対象になった依存をvenv内で上書きしていると、「ノード更新を反映」や自動更新の検証が失敗します（失敗した候補は採用されず、有効環境が維持されます）。
- **検証失敗時の注意点**:
  - 「ノード更新を反映」の検証に失敗した候補は `failed` になり、同じ候補を反映ボタンから再検証できません。「未反映の変更を取り消す」で候補を破棄してから作り直し、必要なノード更新も再実行してください。
- **手動検証による候補環境の修復手順**:
  以下の手順で行う手動検証だけが失敗した場合は、同じ編集中の候補を修復できます。
  1. Managerで候補環境を作り、反映前に候補のPythonで `-m comfy_split.check_environment` を実行して、検証エラーに出るパッケージを確認します。
  2. CPUコンテナで候補の `venv/bin/python -m pip show <PACKAGE>` を実行し、`Location` が候補のvenv内であることを確認します。その候補だけで `venv/bin/python -m pip uninstall <PACKAGE>` を行うと、`--system-site-packages` によりイメージ側の版が使われます（有効環境やイメージ自体のパッケージは削除しません）。
  3. 同じ候補のPythonで `-m comfy_split.check_environment` を実行し、Managerの「ノード更新を反映」で通常のCPU/GPU検証を通してから採用します。
  4. ノード自体が旧版を要求する場合は、候補内で対応版へ更新するか、その候補を破棄します。本体更新前の構成へ戻す場合は、既知のSHAと元のイメージ定義を使って再デプロイします。
  - **依存不足（`pip check` エラー）の補完**: 以前のイメージから継承していた依存が新しいイメージに含まれなくなり、`pip check` が版の競合ではなく依存の不足を報告する場合は、エラーに示された要求を候補の `venv/bin/python -m pip install -c /opt/split-constraints.txt '<REQUIREMENT>'` で補い、上記手順3の検証を通してください。

## 起動プロセスと環境更新

### CPU起動プロセスと初期化画面

1. **Gateway先行起動**: HTTPの入口（Gateway）は環境更新処理より先に起動するため、起動中であっても `GET /split/startup` で進行段階を確認できます。
2. **起動画面の表示**: 準備中はトップページに専用の起動画面が表示されます。
3. **リクエスト待機**: `/split/startup` 以外のAPIリクエストは最大20秒間待機し、準備が完了しない場合は `503 Service Unavailable`（`Retry-After: 2`）を返します。
4. **GPU不起動・清掃タイミング**: 起動確認や画面表示のみでGPUが起動することはありません。保存領域の清掃は起動完了後のアイドル処理で行われます。

### CPU Memory Snapshotによる高速復帰

停止状態から再度画面を開いた際は、CPUコンテナの起動・復元が行われます。

- CPU Memory Snapshotが利用可能で、かつスナップショット保存時と有効環境のバージョンが一致している場合は、初期化済みのComfyUIプロセスを高速に再利用します。
- バージョンが一致しない場合やスナップショットが利用できない場合は通常起動を行います。
- 復元完了後は、最新のジョブ状態とユーザーデータを再読み込みします（詳細は[CPU復元の詳細](../design/cpu-memory-snapshot.md#本体への組み込み)を参照）。

### ノードパックの自動更新

`SPLIT_NODE_PACKS` で指定したノードパックは、デプロイ後の最初のアイドル時（CPU起動時）に更新を確認します。

- カタログに `revision` が指定されている場合は固定コミットを、指定がない場合は配布元リポジトリの既定ブランチ（`HEAD`）を使用します。
- 変更が検出された場合は、候補環境を作成して依存関係とCPUでの読み込みを検査した上で採用します（この自動更新でGPUは起動しません）。
- 更新に失敗した場合は更新前の有効環境を引き続き使用します（再試行条件は[取得と更新](split-integrations.md#取得と更新)を参照）。
- CPUとGPUは、ジョブに固定された同一の環境バージョンを使用します。

## ストレージの整合性と自動清掃

Volumeの構成一覧については、[CPU/GPU分離構成ガイドのVolume一覧](comfyui-split.md#volume-一覧)を参照してください。

### 入出力のコミットとUI通知の整合性

- **実行順序**:
  1. 実行ワーカーは入力ファイルを `reload` した後に生成処理を実行します。
  2. 出力ファイルを `commit` した後に結果を保存します。
  3. CPUは出力ファイルを `reload` してからクライアントへ完了を通知します。
- **通知の保留**: `execution_success` やエラー通知は、出力ファイルの公開と履歴の保存が完了するまで保留されます。
- **フロントエンドのTotal表示対策**: `executed` イベントで完了ノード数を数えるフロントエンドに合わせ、`progress_state` で完了した出力なしノードに対しても空のUI結果を1回通知します。実際の画像・動画を含む結果は出力公開後に通知されます。本体更新時は対応するフロントエンドでTotal表示とプレビューを確認してください。
- **一時出力（`temp`）の処理**:
  - 一時ファイルはコンテナのローカル作業領域で生成され、CPU/GPU実行ワーカーが出力Volumeの `.split-temp/<起動ID>/` へコピーします。
  - 履歴および完了イベントの参照を永続出力へ変換した上で公開します（`.split-temp/temp` に保存された一時出力も `type=temp` で参照・閲覧可能）。
- **ジョブ受付日時の補完**: 待機中・実行中のジョブおよび履歴には受付日時を付与し、保存済みの失敗履歴に不足している項目も補完します。これにより、1件の失敗ジョブが原因でMedia Assetsの一覧全体が読み込めなくなる不具合を防ぎます。

### 自動清掃（クリーンアップ）ルール

保存領域の清掃は、**分離モードのアイドル時（CPU/GPU実行ワーカーのコンテナ数および待機呼び出しがともに0である状態）**に行われます。停止中に清掃のためだけにCPUやGPUを起動することはありません。詳細な設計は[保存構成の設計・変更記録](../design/split-storage.md)を参照してください。

| 対象 | 保護対象 / 保持ルール | 清掃対象 |
| :--- | :--- | :--- |
| **環境 Volume**<br>（`comfy-split-environments`） | 初期環境、有効環境、候補環境、未完了処理が参照中の環境、CPU Memory Snapshotが参照中の環境（`.cpu-snapshots/` に記録） | 左記以外の古い環境（無期限には保管しない） |
| **ジョブ履歴** | 直近7日以内の履歴、および結果不明（`unknown`）ジョブの再実行防止用最小記録 | 完了時刻が記録されてから7日経過した終了済みジョブの詳細履歴 |
| **一時ファイル**<br>（`.split-temp`） | 通常の生成物、入力ファイル、保存済みワークフロー（自動削除対象外） | 更新から24時間以上経過し、かつ履歴や処理から参照されていない一時ファイル |

## API仕様

### ComfyUI標準APIとプロキシ中継

- `/prompt`、`/queue`、`/history`、`/ws`、および `/api/*` を中継・処理します。
- **分離モード（`split`）**: キュー受付、履歴取得、キャンセル、重複受付防止をCPU側で処理します。
- **常時起動モード（`legacy`）**: これらのリクエストをGPU上のComfyUIへ中継します。
- **ジョブ一覧API**: 外部キューのスナップショットを標準拡張へ渡して整形します（ComfyUI内部のキュー・履歴メソッドは差し替えません）。

> [!NOTE]
> **ASGIパスの再エンコード問題（Modal 1.1.4対策）**  
> Modal 1.1.4の標準Webサーバー中継はデコード済みASGIパスを転送するため、`/userdata/workflows%2Fname.json` のようなURLエンコードされたファイルパスの保存・読み込みに失敗します。  
> そのため、CPUの入口は認証付きASGIアプリとして構成し、`comfy_split/modal_proxy.py` でパスを再エンコードして固定版Modalの中継へ渡しています（環境から `raw_path` が提供されている場合はそれを優先）。Modal SDK更新時は `tests/split/test_proxy.py` および公開URL経由でのワークフロー保存・読込を確認してください。

### 追加API一覧

| パス | メソッド | 説明 |
| :--- | :--- | :--- |
| `/split/startup` | `GET` | 起動段階、準備完了・失敗ステータス、CPU Snapshotの復元情報を取得 |
| `/split/status` | `GET` | 現在の動作モード、環境更新状況、結果不明ジョブの有無を取得 |
| `/modal-control/v1/status` | `GET` | 上記と同じ状態を返すバージョン付きAPI（`api_version: 1`） |
| `/split/mode` | `POST` | 動作モードを切り替え（`{"mode": "split"}` または `{"mode": "legacy"}`） |
| `/split/environment/apply` | `POST` | 候補環境を作成・検証して有効環境に反映 |
| `/split/environment/discard` | `POST` | 未反映の候補環境を破棄 |
| `/split/environment/repair-image-browsing` | `POST` | Image Browsingをイメージ同梱版へ戻す候補環境を作成・検証して反映 |
| `/jobs/<id>/cancel` | `POST` | 指定ジョブの待機キャンセル、またはCPU/GPU実行ワーカーへの中断指示 |
| `/jobs/cancel` | `POST` | 複数ジョブの一括キャンセル（`{"job_ids": ["<id>", ...]}`） |

### リクエストヘッダー仕様

- **`Idempotency-Key`（`/prompt` へのリクエスト時）**:
  - 同一キーかつ同一内容の再送に対しては、新規ジョブを作成せず同じジョブIDを返します。
  - 同一キーでリクエスト内容が異なる場合は `409 Conflict` で拒否します。
- **`X-Modal-Execution-Mode: split`（標準ComfyUI APIへのリクエスト時）**:
  - 外部クライアントが明示的に分離モードでの実行を要求するヘッダーです。
  - 常時起動モード中にこのヘッダー付きでリクエストが届いた場合、GPUへの不要な転送を防ぐため `409 Conflict` を返します（状態取得やモード切替などの管理APIは拒否の対象外です）。通常のブラウザ画面はこのヘッダーを付与しないため、両モードを柔軟に切り替えて利用できます。

### 依存関係レポート（`dependencies`）

`/modal-control/v1/status` の `dependencies` フィールドは、実行中のCPU ComfyUI環境における `comfy-kitchen` のバージョン、固定バージョン、および必須APIの不足状況を返します（※GPUカーネルの動作検証とは区別されます）。

- `comfy-kitchen` は上流ComfyUIの指定バージョンを固定依存に含め、イメージ構築時および仮想環境適用時に検査します。
- 保存済み仮想環境が固定版と異なるパッケージを優先している場合は、CPU側のレポートに反映されます。
- 修正が必要な場合はManagerで候補環境の依存を直し、「ノード更新を反映」で検証・採用します（環境検証自体が自動で依存を修復するわけではありません）。

## 障害復旧と二重実行防止

### 2段階コミットと重複実行防止

- **CPU側の2段階ディスパッチ**:
  1. CPUはGPU呼び出し前に `dispatch intent`（投入意図）を保存します。
  2. Modalの呼び出しIDを取得した後に確定情報を保存します。
  3. この間にCPUが停止してIDを記録できなかった場合、ジョブ状態は `unknown`（結果不明）となり、GPU側の結果記録を待ちます。
- **GPU側の重複実行防止**:
  - GPU側も実行前に開始記録を `commit` します。
  - 同一ジョブIDでGPU関数が再度呼び出された際、すでに保存済みの結果があればそれを返します。開始記録しか残っていない場合は `unknown` とし、再実行を行いません。

### 結果不明（`unknown`）ジョブの復旧と運用上の注意

- **結果不明（`unknown`）ジョブの扱い**:
  - 結果不明となったジョブは自動再実行されず、後続ジョブの実行も一時停止します。
  - 管理者はModalのGPU呼び出しログおよび `comfy-split-data/jobs/` の状態を確認した上で手動復旧を行ってください。
  - ネットワークエラーの発生のみを根拠に安易にジョブを再投入してはいけません。
  - なお、GPU関数の実行タイムアウトは「失敗」として確定処理され、結果待ちポーリングのタイムアウトとは区別されます。
- **再デプロイ・併用時の注意事項**:
  - CPUを再デプロイする際は、旧バージョンのCPUコンテナが完全に停止してから新しいCPUを利用してください。状態Volumeへの複数デプロイからの同時書き込みはサポートされていません。
  - 通常構成（`comfyapp.py`）を別途起動している場合、そのGPUはsplit構成の台数制限（最大1台）やUI上の台数表示には含まれません。

## ComfyUI本体との内部連携

- **起動方式**: ComfyUIは `python main.py` で通常通り起動します。キュー読み取り、履歴管理、生成スレッド、一時ファイル削除といった内部処理は上書きしません。分離モードにおける生成受付とGPUへの投入はGatewayが担います。
- **ComfyUI-Modal-Bridgeの役割**:
  - [ComfyUI-Modal-Bridge](../../extensions/ComfyUI-Modal-Bridge/README.md) は、CPUへの直接生成投入を拒否する `PromptQueue.put` ガード機能や、ノード定義取得・ジョブ整形・CPU復元用の内部APIを提供します。
  - これらの内部APIは外部公開Gatewayからは直接アクセスできません。本拡張はsplit構成に必須のコンポーネントであり、任意のAgentBridge中継とは異なります。
- **Managerとパッチの適用関係**:
  - Managerによるインストール処理は候補環境へ中継されます。
  - 通常構成（`comfyapp.py`）で使われているWebSocket圧縮パッチや `user_manager` へのソースパッチは、split構成には適用されません。
- **内部境界変更時の検証**:
  - BridgeやGatewayとの連携境界を変更した際は、`scripts/verify_comfy_bridge.py` によるCPUガードおよびジョブAPIの検証に加え、実モデルでの生成・プレビュー、通常出力・一時出力の保存、CPU再起動後の復元、二重実行防止の動作確認を必ず実施してください。

## 検証・テスト・修復手順

### ログとメトリクスの確認

- 構造化ログに含まれる `comfy_ready`、`gpu_ready`、`gpu_finished`（CPU実行は `cpu_worker_ready`、`cpu_worker_finished`） で起動時間および総処理時間を確認できます。
- モデル読み込みの詳細な所要時間はComfyUI内部ログで、コンテナの停止状況はModal Containers管理画面で確認してください（※GPU Memory Snapshotは本構成では未使用です）。

### ローカル単体テスト

ローカル環境での回帰テストは以下のコマンドで実行します。全体のテスト構成や任意拡張との連携検証については[テストの説明](../../tests/README.md)を参照してください。

```bash
uv sync --locked --extra split-test
uv run --locked --extra split-test python scripts/test_standalone.py --suite split
```

### 実機検証観点と検証スクリプト

実機での受け入れ確認では、ローカルのプロトコルテストだけでなく以下の観点を確認します。

- GPU 0台の状態で10分間ワークフローの編集・保存・閲覧を継続できること
- 画像生成およびリアルタイムプレビューが正常に機能すること
- 生成完了後、停止待ち設定（30秒）に従ってGPUが正常に停止すること
- 連続生成、切断後の再接続、Managerによるノード更新と失敗時の復帰、モードの往復切り替えが正常に行えること

コンテナ内で実行可能な自動検証スクリプトは以下の通りです（いずれも接続先はコンテナ内部の `http://127.0.0.1:8000` を使用し、`SPLIT_URL` は使用しません）。

| スクリプト | 実行場所 / 所要時間 | 検証内容 | 備考 |
| :--- | :--- | :--- | :--- |
| `scripts/verify_split_execution.py` | CPUコンテナ内<br>（短時間） | 2件の投入と待機キャンセル、画像保存・表示、WebSocketイベント、モード往復、GPU停止を確認するAPIスモークテスト | `EmptyImage` を使用するため、モデル推論やサンプリング中プレビューの検証は含みません |
| `scripts/verify_split_idle.py` | CPUコンテナ内<br>（約10分間） | WebSocketを維持しながら、画面配信、メタデータ取得、画像アップロード・表示、ワークフロー保存・読取を繰り返し、各回でGPU台数が常に0であることを確認 | 検証用ファイルは `split-verification` 名で保存されます |
| `scripts/verify_image_browsing.py` | 修復後CPUコンテナ内 | Web拡張配信、一覧表示、アップロード、プレビュー、名前変更、削除、MiniMax生成結果参照を確認 | 出力Volumeの `split-verification/` に `minimax_real_` で始まる画像が存在することが前提です |

> [!IMPORTANT]
> これらのスクリプトによるAPIテストの完了とは別に、Cloudflare Accessを経由した実ブラウザでの操作確認が必須です。

### Image Browsingの修復と検証

Dockerイメージを更新しただけでは、Volume上に保存されている既存ノードは自動更新されません。Image Browsingをイメージ同梱版へ戻す場合は以下の手順を実行します。

1. **修復候補環境の作成**:
   - 認証済みのsplit CPUエンドポイントへ `POST /split/environment/repair-image-browsing` を送信します。
   - アクティブ環境を複製し、Image Browsingのみをイメージ同梱版に戻した候補環境が作成されます（他の追加済みノードも候補環境へ引き継がれます）。
   - 依存関係の検査、CPUおよびGPUでの読み込み検証を通過した後に有効化されます（※GPU検証時に一時的なGPU起動を伴います）。
   - 生成中、キュー待機中、または別の候補環境が存在する場合は `409 Conflict` で拒否されます。
2. **結果確認とロールバック**:
   - 結果は `/split/status` の `candidate` および `environment` で確認できます。
   - 失敗した場合は更新前の有効環境が維持されます。「未反映の変更を取り消す」で候補を破棄してから生成を再開してください。
3. **API検証の実行**:
   - 修復完了後、GPUが0台に戻ったことを確認した上で `scripts/verify_image_browsing.py` を実行します（スクリプト自身が作成した検証ファイルのみ削除されます）。
