# Split構成のCPU/GPU選択と実測データ

[CPU/GPU分離構成（Split）](comfyui-split.md)では、CPU対応済みのAPIと軽い素材入出力だけのワークフローをCPUで実行し、それ以外はGPUで実行します。ワークフロー途中で実行先を切り替えることはありません。

## 選択モードと基本仕様

「GPU」パネルの「GPUの選び方」で選択します。選択はブラウザに保存し、次の受付から適用します。

| 選択肢 | CPU自動実行の対象外だった場合の動作 |
| :--- | :--- |
| **自動（料金優先）** *(既定)* | 既知の外部APIと軽い入出力だけ、または検証済み静止画条件では `L4`。それ以外は `RTX PRO 6000` |
| **自動（速度優先）** | API・軽い入出力は承認待ちがなければ起動中GPUを再利用し、なければ `L4`。ローカル推論は `RTX PRO 6000` |
| **L4 / L40S / RTX PRO 6000** | 指定したGPUを使用 |

CPU対応済みのAPIと軽い読み込み・保存・プレビューだけなら、料金優先とGPU機種の手動指定ではCPUを優先します。**速度優先で承認待ちを挟まない場合は、CPU対応済みでも起動中GPUを再利用します。** 起動中GPUがない場合や稼働状態を確認できない場合は、CPU対応済みならCPU、未登録の既知API・軽い入出力だけならL4へ送ります。「直近の実行先」とMCPの受付・進捗・承認画面で実行先と理由を確認できます。既存の応答項目 `gpu` / `gpu_reason` を維持し、CPUの場合は `gpu: "CPU"` を返します。

常時起動モード（`legacy`）とノード環境検証は従来どおりGPUを使います。UI閲覧・機種選択・状態確認では実行ワーカーを起動しません。

## 自動選択の判定ルール

受付時に**実際に実行する枝（部分実行の指定を含む）**を調べます。CPU対象は [gpu.py](../../comfy_split/gpu.py) の `CPU_API_NODES` と `MEDIA_NODES` で、ノード名だけでなく実装元も照合します。MCPの外部送信・課金確認用リストとは独立しています。GPU検証カタログだけに存在する定義はCPU判定から除外し、UI用CPUで現在読み込めることも必要です。

現時点では、実呼び出し・結果処理のCPU確認が完了したAPIノードはないため、`CPU_API_NODES` は空です。自動CPU実行は確認済みの標準画像・音声・動画の入出力だけで開始します。APIノードと `GeminiToolsSaveAudio` はCPU対応未登録としてGPUへ送り、既存の承認を経た明示CPU試行で確認してから登録します。

- CPU対象のAPI・素材入出力だけ：通常は全体をCPUへ送ります。速度優先での起動中GPU再利用は上記のとおりです。APIを含まない読み込み・保存だけの処理も対象です。
- 小さい `EmptyImage` も対象です。幅・高さ・バッチ数が固定の正整数で、積が `4096²` 以下の場合に限ります。
- ローカル推論・動画フレーム処理・CPU対応未登録のノードを含む：全体を従来のGPU選択へ送ります。理由にはCPU対応未登録または対象条件外のノード名を表示します。
- 外部APIの後ろにローカル生成を接続した場合も、その枝全体が判定対象です。
- 外部APIの承認待ちを挟む場合は、待機中にGPUが停止し得るため起動中GPUを選択に使いません。CPU対応済みならCPU、未登録の既知API・軽い入出力だけならL4へ固定します。
- 選択結果は承認待ちの段階で固定し、同じ受付の再送・再接続で変更しません。過去に受け付けたGPUジョブの実行先は書き換えません。

### 自然言語からCPUで試す

「このワークフローをCPUで試して」と明示された場合、MCPの `enqueue_workflow` に `gpu: "CPU"` を指定します。この指定はCPU対応リストの判定を省略します。通常のブラウザ選択欄にはCPUの手動指定を追加しません。ブラウザのCPU指定Cookieは自動選択として扱い、リクエスト本文でのCPU指定は拒否します。

**MCP未対応のノードや、外部送信内容を確認できないノードはCPU指定でも拒否します。** 外部APIの承認・素材の固定・認証情報の取り扱いは従来どおりです。CPU実行に失敗してもGPUへ自動再実行せず、対応リストにも自動登録しません。再試行する場合は新しい `request_id` を使います。

### CPU実行基盤の検証

```bash
scripts/modal.sh run -m scripts.verify_split_cpu
```

一時的なCPUコンテナで、UIとは別の実行用ComfyUIを起動し、画像・音声・動画の読み込み・保存とプレビューを確認します。本番Volumeは読み取り専用で、入出力は検証コンテナ内に保存します。CPU利用料は発生しますが、GPUと外部APIは呼び出しません。APIノードのCPU対応確認には、別途、承認を経た実呼び出しと返却データ処理の確認が必要です。

### CPU対応を追加する手順

「CPU対応未登録」はインストール済み・GPU実行成功とは別の状態です。次の確認を行い、対象リストを更新してデプロイした時点で自動実行の対象になります。

1. 対象ノードの実装元と版を確認し、最小の入力と保存・プレビューを含むAPI形式のワークフローを用意します。
2. `gpu: "CPU"` でCPU実行ワーカーへ投入します。MCP未対応のノードは、まず送信先・入力・課金の扱いを確認してMCP側の対応を行います。外部APIの実呼び出しは既存の承認経路を使います。
3. CPU上でのインポート、API呼び出し前後の処理、結果の保存・表示を確認します。GPU 0台から開始し、実行中もGPUが起動しないことを確認します。画像だけでなく、そのノードで使用する音声・動画入力や出力も対象にします。
4. `CPU_API_NODES` または `MEDIA_NODES` に実装元とノード名を追加します。確認した版・入力条件・結果を変更の検証記録に残し、振り分けテストを実行します。MCPで許可されるだけではCPU対応済みにはしません。
5. Modalを更新後、MCPの入力仕様・説明を変更した場合はWorkerも更新します。

### CPU実行未対応版へ戻す手順

旧版はジャーナルの `gpu: "CPU"` を実行できません。戻す前に、ブラウザとMCPからの新規投入を止め、待機ジョブを取り消し、実行中ジョブの完了または取消完了を確認します。`unknown` が残る場合は既存の復旧手順で解消し、キューを空にします。外部APIの承認待ちもすべて拒否または期限切れにし、未承認のCPU指定が後からジョブ化されない状態にしてから戻してください。完了済み履歴は削除不要です。

ModalとWorkerを対応する旧版へ戻した後に受付を再開します。CPUジョブや承認待ちを残したまま旧版へ戻すとキューが停止するため、その場合はまずCPU対応版を再デプロイし、上の整理を行います。

## 実行基盤と切替

CPU実行ワーカーはUI用CPUと別コンテナで、2 vCPU・8 GiB、最小0台・最大1台、停止待ち30秒です。GPUを割り当てず `--cpu` でComfyUIを起動し、既存のイメージ・Secret・環境・Volumeと、キュー・承認・進捗・キャンセル・結果保存の処理を共有します。UI・候補環境の実行禁止ガードは維持します。

ジョブは従来どおり1件ずつ実行します。GPU機種間の切替では前のGPUコンテナの停止を待ちますが、CPUとGPUの切替では処理済みコンテナのアイドル停止を待ちません。保存領域の清掃ではCPU実行ワーカーの稼働も確認します。GPU台数にはCPU実行ワーカーを含めません。

CPUにもコールドスタートがあり、CPU利用料・外部API料金は発生します。CPUジョブを投入しても、前のGPUジョブの停止待ちが即座に終わるわけではありません。

## 静止画生成の実測データ（FLUX.3 Klein）

料金優先・速度優先の判定基準として、FLUX.3 Klein（int8版）のテキストからの静止画生成を実測しています。

### 対象条件（自動判定の照合条件）

以下の条件をすべて満たすワークフローを「検証済みの静止画生成」として照合します（ノードIDや保存ファイル名は任意です）。

- **照合対象**: モデル、テキストエンコーダー、VAE、実行ノード、入力条件（FLUX.3 Klein int8 のテキストからの生成）
- **生成パラメータ**: SageAttention 有効、バッチサイズ 1、解像度 `512×512` または `1024×1024`、サンプラー `euler`、スケジューラー `simple`、4ステップ、CFG `1`

### 初回生成の料金・所要時間比較（コールドスタート）

各機種・解像度ともGPU 0台の状態から開始し、「ComfyUIの起動 → モデル読み込み → 生成 → PNG保存の確認」までの時間に [ModalのGPU秒単価](https://modal.com/pricing) を掛けて算出しています。

| 初回生成（各条件1回） | L4（`$0.000222`/秒） | L40S（`$0.000542`/秒） | 料金優先での採用機種 |
| :--- | :--- | :--- | :--- |
| **512 × 512** | 50.16秒・`$0.01114` | 23.17秒・`$0.01256` | **L4** |
| **1024 × 1024** | 37.20秒・`$0.00826` | 26.84秒・`$0.01455` | **L4** |

> [!NOTE]
> - GPUの割り当て待ち、コンテナ初期化、生成後のアイドル待機時間、外部API料金は上表の計算対象外です。
> - 各解像度を別の初回生成として1回ずつ計測した観測値であり、モデル読み込みやVolumeキャッシュなど実行条件の揺らぎを含みます（512pxと1024pxの純粋な解像度差を示すものではありません）。

### モデル読み込み済みでの実行速度比較（ウォーム実行）

速度優先の判断には、同じ `1024×1024` グラフでモデル読み込み済み状態でのComfyUI実行時間（各機種1回測定）を使用しています。

- **L4**: `2.79秒`
- **L40S**: `0.91秒`
- **RTX PRO 6000**: `0.67秒`（速度優先で採用）

### 再計測コマンド

同じ[検証用グラフ](../../scripts/verify_split_gpu_workflow.json)を3機種で再計測するには、デプロイ済みComfyUIのコミットSHAを指定して以下のコマンドを実行します。

```bash
# 全機種・全解像度で計測
SPLIT_COMFYUI_REVISION=<DEPLOYED_COMFYUI_SHA> scripts/modal.sh run -m scripts.verify_split_gpus

# 機種や解像度を絞って計測する例
SPLIT_COMFYUI_REVISION=<DEPLOYED_COMFYUI_SHA> scripts/modal.sh run -m scripts.verify_split_gpus --gpu L4 --size 1024
```

- `SPLIT_COMFYUI_REVISION`（SHA）の指定は必須です。`.env` からも読み込みますが、シェルでの指定が優先され、測定結果にも実際のSHAが記録されます。
- モデルVolumeは読み取り専用で接続され、検証用PNGは一時領域に保存されます。
- イメージは現在のチェックアウトから構築するため、本番との比較には同じリポジトリのコミットとデプロイ設定を使用してください。

## 音楽生成の実測データ（L40S）

2026-11-06に、保存済みの成功ワークフローを基に `L40S` で計測した結果です。バッチ1・SageAttention有効で、既存Volumeからモデルを読み取り、ケースごとにGPUを0台へ停止させてから次のケースを起動しています（全4件とも生成・MP3保存に成功）。

| モデル | 音声の長さ | ComfyUI実行時間 | ComfyUI起動から保存まで | 観測最大VRAM | 主な設定 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **ACE-Step 1.5 XL Turbo bf16** | 30秒 | 22.83秒 | 41.43秒 | 16.0 GiB | Qwen 0.6B＋1.7B エンコーダー、ACE 1.5 VAE、音声コード生成あり、`euler`/`simple`・8ステップ・CFG 1 |
| **ACE-Step 1.5 XL Turbo bf16** | 180秒 | 27.70秒 | 40.00秒 | 29.7 GiB | 同上 |
| **YuE2 3B bf16** | 30秒 | 32.75秒 | 48.08秒 | 9.0 GiB | `full` モード、`dpm_2`/`sgm_uniform`・32ステップ・CFG 1、タイルVAEデコード |
| **Stable Audio 3 Medium** | 30秒 | 10.74秒 | 26.17秒 | 6.6 GiB | T5Gemma エンコーダー、`lcm`/`simple`・8ステップ・CFG 1 |

- **計測条件と確認項目**:
  - 実行時間はモデル読み込みを含みます（GPUの割り当て待ち・コンテナ初期化は含みません）。
  - 観測最大VRAMは、生成中に約250ms間隔で取得したデバイス全体の使用量です。
  - 各試行でMP3のデコード、指定時間との一致、有限値かつ無音でない音声データ、試行後のGPU 0台復帰を確認しています。
- **現在のGPU選択における扱い**:
  - 上記の条件では `L40S` を直接指定して生成できます。
  - 音楽生成については `L4`・`RTX PRO 6000` との同条件での料金比較が未完了のため、自動選択では `RTX PRO 6000` を使用します。
